# PKMS Google Drive (`@pkms/google-drive`)

Shared Google Drive API and workspace repository used by PKMS platform adapters.

- `GoogleDriveClient` owns Drive v3 requests, authentication-token injection, bounded rate-limit retries, immutable operation upload recovery, and change-feed paging.
- `GoogleDriveClient.searchFullTextPage` exposes Drive's indexed `fullText` query as a bounded page; `GoogleDriveWorkspaceRepository.searchFullTextPage` filters those results to Markdown files beneath the selected root. Drive matches whole tokens and quoted phrases, not arbitrary substrings, so this API primitive does not replace the editor's exact local-content search contract.
- `GoogleDriveWorkspaceRepository` maps one explicitly selected Drive folder to a recursive PKMS tree and exposes file, folder, move, rename, and trash operations. `listDirectoryById` and `getEntry` resolve stable item IDs and fetch only the requested tree branch, without enumerating unrelated directories. Moving a folder checks only the source/target ancestry and destination path; it does not recursively list the workspace. `createFolderOnce` and `createFileOnce` recover a successful Drive create after a lost response by a workspace-scoped operation marker and reject payload collisions. `resolveGoogleDriveWorkspaceRoot` discovers roots by an app-owned `appProperties` marker across devices, creates one only when none exists, and stops when roots are ambiguous.
- `IndexedDbDriveOutbox` stores stable, ordered operations and content bytes locally; an operation remains pending until its caller confirms durable Drive acknowledgement.
- `IndexedDbGoogleDriveReplica` stores per-root metadata, on-demand cached bytes, and the Drive changes cursor. It applies change pages before advancing the cursor and preserves cached descendants with pending edits when a remote folder is removed.
- `GoogleDriveOperationLog` writes immutable, checksummed operation records under the hidden `.pkms-sync/operations` folder. Drive `appProperties` index each operation's workspace, type, and affected item. Sync reads operation file contents only from the Drive changes feed after a replica's durable cursor; initial connection establishes a baseline instead of replaying all history. Opening a Markdown file queries and downloads only that file's seed and Yjs updates.
- `GoogleDriveYjsDocumentStore` lazily opens one Markdown document at a time, seeds it from its pending create, its deterministic seed operation, or that Drive file, and queues local Yjs updates. It does not bulk-download or index all file contents. The product search index and platform adapters still need to be integrated separately.
- `GoogleDriveOperationApplier` replays tree operations and delegates Yjs/document and asset projection. `GoogleDriveAssetConflictMaterializer` resolves one asset's immutable replacement history in deterministic operation order, retains divergent older byte versions as stable visible conflict files, and projects the same winner on every replica. Because operations do not yet carry a causal base hash, this conservative rule may expose sequential historical versions as conflict files; full binary editing and base-aware conflict UX remain incomplete.
- `GoogleDriveSyncEngine` appends durable outbox entries to that log, reads incremental changes after a root-scoped durable cursor, replays those operations through an injected idempotent reconciliation callback, and only acknowledges local work after reconciliation and cursor persistence succeed. The concrete reconciliation/projection implementation is still required from a product adapter.
- `createGoogleDriveWorkspaceSync` composes the repository, operation log, durable outbox, and Yjs document store into one replay pipeline. Web and Desktop connect the shared asset conflict materializer; platform-specific adapters supply durable stores and authentication.
- `GoogleDriveWebOAuth` performs foreground-only Web authorization and keeps access tokens in memory. It requests reauthentication after expiry and does not save tokens to browser storage.
- The `/` Web route now defaults to Google Drive and reuses the shared Markdown editor and direct Drive repository for branch listing, Markdown open/edit/save, basic tree mutations, and `Cmd/Ctrl+Shift+F` Drive-indexed word/phrase search scoped to workspace Markdown. `/existing-pkms` retains the previous API-backed PKMS UI as a migration fallback. Search does not yet provide arbitrary substring matching, matching-line previews, or offline full-workspace coverage. The sync pipeline preserves and projects binary replacement operations, but the Web route does not yet offer binary editing; complete migration and remaining PKMS features are not connected yet.
- Desktop now has a main-process workspace service and restricted preload IPC for root discovery/creation, branch listing, Markdown open/save, basic tree mutations, and sync. A native SQLite adapter persists the operation outbox and Yjs snapshots with WAL and full synchronous commits. The PKMS pane defaults to this direct Drive mode and retains the existing PKMS source as an explicit migration fallback. The native OAuth client ID still must be registered/configured before account-level Desktop runtime verification.
- OAuth consent, token persistence, durable local outbox, Yjs operation orchestration, and platform UI belong to Web and Desktop adapters in the current implementation scope. iOS can implement the same provider contracts in a later phase. This package does not use a PKMS server or Worker.

The target storage and synchronization contract is documented in [Google Drive direct sync](../../docs/architecture/pkms/google-drive-direct-sync.md). The package is a shared foundation; its existence alone does not switch a product client away from the current PKMS API.
