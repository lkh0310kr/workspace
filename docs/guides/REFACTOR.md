# 리팩터링 원칙

내가 생각하는 좋은 리팩터링은 코드를 짧게 만드는 일이 아니다. **사용자에게 보이는 동작은 지키면서, 다음 변경을 더 적은 위험과 적은 중복으로 할 수 있게 구조를 바꾸는 일**이다. 공통화나 새 추상화 자체를 목표로 삼지 않고, 책임과 데이터 흐름을 분명하게 만드는 것을 우선한다.

## 1. 동작과 구조를 구분한다

- 리팩터링만 하는 변경은 입력, 결과, 오류 처리, 저장 시점, 접근성, 키보드·포인터 동작을 보존한다.
- 제품 동작을 바꿔야 한다면 구조 변경에 숨기지 말고 요구사항과 수락 기준에 명시한다.
- 코드를 옮기기 전에 현재 동작의 소유자, 호출 경로, 상태 수명, 외부 경계를 확인한다. 화면 한 곳의 증상은 파일 열기·동기화·IPC처럼 다른 경계에서 비롯될 수 있다.
- 현재 구현과 목표 동작이 다르면 둘을 문서에서 구분한다. 코드를 근거로 삼되, 현재 코드가 곧 제품 의도라고 가정하지 않는다.

## 2. 경계와 소유자를 먼저 정한다

- 상태를 만들고 갱신하는 곳, UI를 그리는 곳, 영속화하는 곳, host와 통신하는 곳을 구별한다.
- 공통 모듈은 여러 host에서 실제로 같은 계약과 수명을 갖는 동작을 소유한다. host 차이는 capability, adapter, slot, 명시적 설정으로 전달한다.
- 한 모듈이 여러 역할을 떠안거나, 상위 앱이 내부 구현을 직접 조작하거나, 공통 컴포넌트에 host별 조건문이 계속 늘어나면 경계를 다시 나눈다.
- 중복 코드가 있다는 사실만으로 공통화하지 않는다. 동작과 변경 이유가 다르면 별도 소유자로 두고, 계약이 같아질 때 통합한다.
- 의존 방향은 바깥의 host가 안쪽의 공통 기능을 사용하도록 한다. 공통 package가 특정 앱이나 host의 구현을 역으로 참조하게 만들지 않는다.

## 3. 상태와 데이터 흐름을 먼저 정리한다

- 각 상태의 생성·갱신·취소·정리 시점을 명확히 한다. 오래된 응답, 중복 요청, 재시작, 빠른 연속 입력을 고려한다.
- 사용자가 기다리는 동안에는 작업 시작과 현재 상태를 바로 보여 준다. 실제 저장·업로드 완료를 확인하기 전에 완료로 표시하지 않는다.
- 파일·폴더의 식별자와 경로, 문서 세션과 편집기 view 상태처럼 의미가 다른 값을 한 값으로 뭉개지 않는다.
- 전역 상태나 이벤트 버스는 소유권과 수명이 분명한 경우에만 쓴다. 호출 관계를 숨기거나 상태 변경을 추적하기 어렵게 만들면 명시적인 함수·adapter로 바꾼다.
- 실패는 복구 가능한 형태로 처리하고, 필요한 오류 정보와 다음 행동을 사용자 또는 로그에서 확인할 수 있게 한다. 비밀값과 민감한 문서 내용을 오류에 넣지 않는다.

## 4. 공통 UI와 스타일은 한 곳에서 소유한다

- Editor와 TreeView처럼 여러 host가 공유하는 UI 구조·동작·기본 스타일은 공용 package가 소유한다. host에는 필요한 구성과 capability 차이만 둔다.
- 스타일은 컴포넌트별 CSS Module에 둔다. 하나의 거대한 stylesheet를 컴포넌트 이름만 바꾸어 복사하지 않는다.
- 전역 CSS는 디자인 토큰과 꼭 필요한 host reset 정도로 제한한다. 외부 라이브러리 selector가 필요하면 공용 컴포넌트의 로컬 root 아래로 범위를 좁힌다.
- host가 공용 UI를 꾸밀 때는 전용 slot, semantic token 또는 명시적 data hook을 사용한다. 생성된 CSS Module class를 다른 모듈의 API처럼 참조하지 않는다.
- padding, border, radius, shadow는 기존 계약이나 확인된 사용성 근거가 있을 때 추가한다. 요소를 상자처럼 보이게 하려고 관성적으로 넣지 않는다.
- 색상·간격·행 높이·글꼴을 여러 host에서 따로 정의하기 전에 공통 토큰과 공통 컴포넌트가 소유할 수 있는지 확인한다.

## 5. 작은 구조 변경을 선호하되, 문제의 경계까지 고친다

- 관련 없는 파일의 재정렬, 대규모 포맷 변경, 사용하지 않는 스타일·코드 정리는 요청된 구조 변경과 분리한다.
- 반대로 보고된 문제가 경계나 수명주기에 있으면 화면 한 줄만 고치는 데서 끝내지 않는다. 실제 책임을 소유한 계층까지 수정한다.
- 아직 필요하지 않은 범용 프레임워크, 설정 옵션, 호환 계층을 미리 만들지 않는다. 반복되는 사용 사례와 계약이 확인된 뒤 추상화한다.
- 오래된 코드를 제거하기 전에는 호출부, 공개 export, 저장 데이터, 마이그레이션, 외부 소비자를 검색한다. 쓰이지 않는다는 증거와 안전한 제거 경로를 확인한다.
- 대형 모듈은 도메인 책임이나 변경 이유에 따라 분리한다. 줄 수를 맞추려고 무관한 조각으로 쪼개지 않는다.

## 6. 검증은 구조에서 동작까지 쌓는다

1. 타입·정적 계약으로 의존 방향, 모듈 소유권, 필수 hook과 접근성 계약을 확인한다.
2. 단위 검증으로 순수 규칙과 오류·취소·재시도 동작을 확인한다.
3. 통합 검증으로 UI에서 provider, 저장소, IPC, host까지 실제 경로를 확인한다.
4. host가 여러 개면 공통 입력에 대해 계산된 값과 결과를 비교한다. 스크린샷은 최종 외관 회귀를 찾는 보조 수단으로 쓴다.

스크린샷 차이는 원인을 설명하지 않는다. 먼저 컴포넌트 소유권, cascade, 상속, 레이아웃 계산, host 경계를 확인한다. 생성된 class 이름이나 이미지 픽셀만 맞추는 수정으로 문제를 가리지 않는다. 스크린샷 기준을 바꿀 때는 실제 화면을 검토하고, 의도한 변화가 무엇인지 설명할 수 있어야 한다.

## 7. 작업과 커밋을 검토 가능하게 유지한다

- 구현 전에 담당 규칙·스펙과 현재 worktree를 읽는다. 기존 사용자 변경은 보존하고 관련 파일만 수정한다.
- 코드 변경과 함께 소유 스펙, module export, 정적 계약, 사용자 문서를 필요한 범위에서 갱신한다.
- 완료된 독립 작업마다 명시적 파일만 stage하고 staged diff와 검증 결과를 확인한 뒤 별도 커밋한다.
- 검증하지 않은 항목은 통과했다고 말하지 않는다. 실패한 검증은 원인을 고치고 다시 실행하거나, 남은 제한을 결과에 분명히 적는다.

## 작업 전후 점검

- 이 변경이 보존하거나 바꾸는 사용자 동작은 무엇인가?
- 상태·스타일·저장·host 연결의 단일 소유자는 어디인가?
- 같은 계약을 소비하는 다른 host와 공개 호출부를 확인했는가?
- 공용화가 실제로 중복 책임을 줄이는가, 아니면 host 조건만 늘리는가?
- 필요한 구조·동작 검증을 실행했고, 실패와 미검증 범위를 기록했는가?
- diff에서 무관한 변경을 제거하고 독립된 작업 단위로 커밋했는가?
