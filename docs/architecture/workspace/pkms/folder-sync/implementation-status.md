# Folder sync 현재 구현·배포 상태

이 문서는 `2026-11-14` source 및 원격 상태 review snapshot이다. 목표 동작은 [contract](./README.md)와 하위 계약을 본다. 이 페이지의 수치와 helper 구조는 구현 관찰이며 미래 구현의 요구가 아니다.

## Persisted schema source shape

현재 `Persisted` top-level field: `configs`, `baselines`, `remoteFiles`, `syncCursors`, `remoteTrees`, `remoteTreeVersions`, `pendingPaths`, `pendingUpdates`, `pendingCreates`, `pendingFolderCreates`, `localDirectories`, `pendingDeletes`. field별 의미는 [durability contract](./durability-recovery.md)에서 정규 정의한다. JSON 파일에는 명시적 schema version/migration registry가 아직 없다.

`pendingCreates`/`pendingUpdates`/`pendingDeletes`에는 operation identity와 재시도에 필요한 payload/guard 일부가 있다. `pendingPaths`는 dirty path hint이며 모든 파일 변경 payload를 담은 operation journal은 아니다. directory inventory와 pending delete는 durable, item UI state는 현재 status memory다.

## 남은 root 전환 수락 항목

Source는 새 설정을 저장하기 전에 root에서 파생된 상태를 초기화한다. 이로써 확인된 stale-baseline 삭제 경로를 막는다. 기존 cloud file이 있는 상태에서 빈 임시 root로 전환하고, 새 root에 file이 materialize되는 동안 cloud ID/revision/body hash가 유지되는지 확인하는 fake-server integration scenario가 필요하다. 두 번째 scenario에서는 새 root에 로컬 전용 파일과 같은 path의 다른 내용을 넣어 import와 conflict 보존을 확인한다. 두 scenario를 통과하기 전에는 root 전환 end-to-end 수락을 완료로 보지 않는다.

## 현재 사용자에게 보이는 동작

`SyncBridgePanel`은 5초 poll로 status를 읽는다. Main status는 `disconnected/syncing/synced/offline/error`, item state는 `pending/syncing/attention`이다. 가변 aggregate `completed/total` 퍼센트는 제품 UI에서 제거했고 conflict path button은 editor 열기로 연결했다. durable conflict review/resolve queue는 제공하지 않는다. UI는 GitHub backup 상태도 함께 보여주지만 distinct channel로 표시한다.

## GitHub 방향과 실시간 배포 상태

- GitHub는 초기 repository import 후 PKMS database에서 내보내는 backup 경로다. 이후 GitHub branch 변경은 현재 자동으로 cloud로 import/merge하지 않고 `external-change` 상태에서 자동 push를 멈춘다. 따라서 direct Git edits와 PKMS cloud edits가 같은 파일을 바꿨을 때 자동 수렴은 구현되어 있지 않다.
- 2026-11-13 원격 확인에서 workspace가 `external-change`였고 로컬 Git branch와 cloud가 기록한 Git head가 달랐다. 이 상태에서는 양쪽 변경을 보존하는 reconciliation 없이 branch reset이나 강제 push를 수행하면 안 된다.
- 원격 Supabase에 빠져 있던 `20261109160000_guarded_sync_deletes.sql`을 2026-11-13 적용했다. 이 migration은 이후 destructive sync operation의 revision guard를 보강하며 기존 파일 row를 수정하지 않는다.
- 2026-11-13 `20261113100000_dedupe_identical_sync_creates.sql` 적용. 같은 경로·같은 본문 create retry는 기존 item을 반환하며, 본문이 다를 때만 conflict path를 만든다. `supabase/tests/20261113100000_dedupe_identical_sync_creates.sql`를 linked DB에서 트랜잭션 rollback 방식으로 실행해 동일 본문 Markdown, operation retry, 다른 본문 보존, 같은 folder 생성 수렴을 확인했다.
- `conflict desktop` 사본 복구: 활성 Cloud Markdown 842개와 local 846개 모두 원본과 본문/hash가 같아 안전하게 정리했다. Cloud 사본은 guarded operation으로 tombstone 처리했고 local copy와 두 빈 충돌 폴더를 제거했다. 다른 내용이었던 과거 `guitaringo.md` conflict row는 기존 tombstone 이력을 보존했고 최신 원본은 유지했다. 복구 전 Cloud snapshot과 local 경로/hash manifest는 `~/Library/Application Support/workspace-app/pkms-recovery-20261113/`에 보관한다.
- Local↔Cloud 본문 검증: 활성 Markdown 3,706개 전부 로컬 파일과 Cloud Yjs 본문이 byte-for-byte 일치했다. Yjs state가 비어 있는 18개는 같은 revision-0 Git blob SHA로 확인했다. conflict 정리 후 Desktop PKMS에서 complete sync를 실행했다. persisted cursor 2,638이 Cloud revision 2,638과 같고 baseline/remote cache 각각 3,706개, pending path/create/update/delete 모두 0개임을 확인했다. 패널도 `Up to date`, 100%를 표시했으며 active conflict copy는 0개다.
- Cloud↔GitHub 복구 완료: 기존 GitHub `main` head `a54094655faa89a7c2263325ea0e8430062f9533`를 parent로 둔 일반 commit `7af23452cc28b4651a0f7dbf7bf05c719331291c`을 만들어 Cloud 활성 tree로 전진시켰다. force update 없이 완료했다. 최종 12,472개 경로의 SHA/mode 비교에서 차이 0개, Cloud `github_head=mirrored_head=7af23452cc28b4651a0f7dbf7bf05c719331291c`, `github_status=synced`, dirty row 0을 확인했다.
- 최종 Cloud tree와 현재 GitHub `main` tree가 일치하지만 direct Git edits는 여전히 자동 Cloud import/merge하지 않는다. branch가 외부에서 바뀌면 `external-change`로 멈추고 tree reconciliation 후 일반 commit으로 복구한다. force push/reset은 복구 절차가 아니다.
- Root/workspace source가 다르면 local scan의 deletion inference를 차단해야 한다. 이 guard는 기존 open issue라 전체 recovery acceptance에서 별도 통과가 필요하다.

- 동기화 수정은 `940f53e` (`fix(pkms-sync): reconcile missing folder metadata`)에 커밋했다. 로컬 검증: `npm run pkms:server:typecheck`, `npm --prefix apps/workspace-app run test:sync` (9 tests), `npm --prefix apps/workspace-app run typecheck`, `npm run pkms:web:typecheck`, `npm run pkms:web:build`, `git diff --check` 통과.

- `pkms-cloud` 배포 완료: `https://pkms-cloud.lkh0310kr.workers.dev`, version `0ef90099-497d-448e-8e0c-a3560cb7a068`; `/api/health`는 HTTP 200. `pkms-web` 배포 완료: `https://pkms-web.lkh0310kr.workers.dev`, version `d997490c-69ef-4de5-8118-ccb8c725e1b6`; 이 주소는 설정된 canonical origin인 `pkms-cloud`로 HTTP 302 redirect한다.
- Web realtime tree 회귀 수정 배포: `282da5f`에서 Markdown-only `/snapshot` 응답으로 `files` state 전체를 덮던 동작을 제거하고 loaded `/directory` 응답을 재조회하도록 바꿨다. `pkms:web:typecheck` 및 production build 통과. 2026-11-14 배포 Worker version `6ff6adc0-6456-4388-8e55-229188fd2a84`; cloud directory rows에서 새 root folders 3개가 active `kind=folder`로 확인됐다.
- 2026-11-14 tree responsiveness/recovery 수정: directory open은 queued operation flush를 기다리지 않고 요청한다. IndexedDB cache는 먼저 보이고, 열어 본 directory 및 직계 하위 folder listing을 최대 8개 동시 요청으로 background refresh한다. queue rejection 및 move/delete recovery가 Markdown-only `/snapshot`으로 Files tree를 덮지 않고 loaded `/directory`를 재조회하도록 수정했다. PKMS iOS도 workspace tree metadata와 loaded directory 목록을 Application Support에 저장하고 재열기 때 cache-first로 표시한다.
- 2026-11-14 저지연 local 반영 및 tree action 정책 수정: Web Markdown autosave idle debounce를 5초에서 400ms로 줄였고 Desktop Cloud revision fallback poll을 30초에서 5초로 줄였다. Realtime wakeup은 계속 주 경로다. PKMS toolbar의 upload/delete/rename 제거는 source에서 확인했으며 keyboard Delete/F2와 title-click rename도 제거해 해당 항목은 tree context menu에서만 시작한다. Upload도 context menu에 연결했다. dismissible error toast는 viewport 오른쪽 아래로 이동했다. 실제 Web↔Desktop local-file hash와 hit-target 수동 acceptance는 남아 있다.
- 위 PKMS Web source를 `pkms-web` Worker version `1830a1b0-3980-4d8f-b0bd-e4c1d15a0ccf`으로 배포했다. 마지막 배포에는 Delete/F2 입력 차단과 오류 알림 본문이 pointer event를 가로채지 않는 hit-target 수정이 포함됐다. `pkms:web:typecheck`, Web production build, Workspace app typecheck/build가 통과했다. 열린 Web tab은 reload하지 않아 실제 화면 hit-test는 미확인이다. Workspace app process가 실행 중이어서 이를 종료/교체하지 않았다. 따라서 5초 Desktop fallback poll은 build source에는 있으나 현재 실행 중인 binary에는 아직 적용되지 않았다; 현재 binary의 Realtime sync 경로는 유지된다.
- 2026-11-14 folder delete conflict 보정: `20261114160000_scoped_folder_delete_guard.sql`을 production `pkms-cloud`에 적용했다. `supabase/tests/20261114160000_scoped_folder_delete_guard.sql`를 linked production DB에서 transaction rollback으로 실행했다. unrelated workspace revision은 folder delete를 막지 않고, base 이후 대상 subtree revision이 존재하면 `folder_changed_since_base`가 발생함을 확인했다. remote migration list에서 local/remote version이 일치한다.
- 2026-11-14 Web tree/cache 및 recovery 수정의 `pkms-web` Worker 배포 version은 `1236ce56-5912-41c2-9351-d30c9a056f95`다. 배포 전 `pkms:web:typecheck`와 production build를 통과했다. 현재 열린 브라우저 화면은 강제 reload하지 않았으므로, 새 번들은 다음 새로고침에서 적용된다.
- 2026-11-14 Desktop 재실행 검증에서 기존 `syncCursors[workspaceId]`가 Cloud change-feed 범위 밖으로 밀린 `invalid_sync_cursor`를 발견했다. 이전 bridge는 이를 복구 불가 error로 노출해 Cloud→local sync를 중단했다. 이제 해당 오류에 한해 authoritative snapshot + complete local scan으로 reconcile한 뒤 cursor를 갱신한다. 동일 경로에 양쪽 변경이 있으면 기존 conflict-copy 정책을 적용한다. 새 build 설치와 stale-cursor recovery 수동 acceptance는 아직 남아 있다.
- 현재 Web editor에서 열린 문서를 방해하지 않도록 브라우저 페이지를 강제로 reload하지 않았다. production DB의 root directory row와 API health, Worker 배포 버전을 확인했다. 실제 브라우저에서 새로고침 후 화면 표시 확인은 아직 수행하지 않았다.
- [local deletion](./deletion.md)의 inventory/pending delete/guarded delete는 source에 있다.
- migration 적용은 `supabase migration list --linked`로 확인했다. 중복 create 회귀 SQL, 현재 7개 sync policy unit test, `npm run check:app`은 통과했다. 전체 `npm test`는 626 passed, 2 skipped, 8 failed로 끝났으며 실패는 shortcut 2, `global.gc`가 없는 queue-retention 3, CodeMirror extension 1, TreeView display-name 1, closeTab 1이다. 이들은 이번 sync 변경과 무관한 기존 실패로 분류하되 전체 suite는 green이 아니다.
- 원격 Cloud/Git tree reconciliation, local complete pass 및 데이터 hash 검증은 완료했다. `syncBridge` end-to-end behavioral test와 앱 재시작 후 상태 유지 검증은 여전히 없다. 현재 local↔Cloud 일치 상태와 code-level failure recovery 검증은 구분해서 보고한다.
- local folder rename (stable inode), empty folder, interrupted delete, dropped watcher, lost successful HTTP response, JSON corruption, disk full, server migration mismatch에 대한 실제 acceptance가 남아 있다.
- 아래 acceptance matrix의 root-switch fake-server fixture, 재시작, lost acknowledgement, macOS watcher, 다중 기기 충돌 fixture와 server transaction race가 필요하다.
