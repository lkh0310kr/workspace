# PKMS 동기화 종단 간 검증 체크리스트

이 체크리스트는 특정 플랫폼의 화면이나 구현 방식이 아니라 **우리 프로젝트가 보장해야 하는 동기화 결과**를 기준으로 한다. 사용자가 어느 연결 지점에서 자료를 바꾸든 모든 replica가 같은 workspace와 file identity를 기준으로 수렴해야 한다. 한 구현이나 한 실행 환경에서 성공한 동작만으로 다른 연결 지점, 재시작, 네트워크 장애까지 증명되지는 않으므로, 검증 근거에는 실제로 확인한 경계와 남은 경계를 함께 적는다.

Web·iOS·Desktop 같은 client 이름은 관찰한 검증 근거를 설명할 때만 쓴다. 제품 요구사항과 완료 판단은 client별 기능 목록이 아니라 변경 결과, replica 간 수렴, 장애 후 복구로 공통 평가한다.

## 목표 결과

사용자가 만든 파일·폴더·본문 변경은 명확한 상태와 함께 durable 저장소에 기록된다. 연결된 replica는 같은 내용을 다시 읽을 수 있고, 실패·재시작 뒤에도 미확인 변경이 복구된다. 동시 변경, 삭제, 이동, 권한 오류가 발생하면 어느 쪽 자료도 조용히 유실되지 않는다. 캐시, 공통 저장소, 선택적 backup은 각각의 책임과 성공 상태를 구분한다. 예를 들어 GitHub backup 완료는 PKMS cloud sync 완료와 별도 결과다.

## PKMS sync 경계

- 현재 운영 경로에서 PKMS cloud workspace가 문서 및 파일 tree의 공통 저장 기준이다. Web과 iOS는 cloud API/Yjs를 사용한다. Desktop은 같은 cloud에 연결하고 사용자가 지정한 local folder를 mirror한다.
- Realtime은 변경을 빨리 알리는 수단이다. 변경의 진실과 복구 기준은 durable cloud revision/change feed 및 authoritative snapshot이다.
- Yjs는 Markdown 본문의 concurrent update를 합친다. 파일 identity, path, 폴더 계층, delete, binary asset conflict는 별도의 sync operation이 소유한다.
- GitHub는 별도 선택 backup이다. PKMS cloud에서 `synced`라고 해서 GitHub backup도 완료된 것은 아니다. 외부 GitHub 변경은 자동 overwrite하지 않고 divergence 상태로 멈춘다.
- Google Drive direct prototype은 격리 실험이며 현재 PKMS sync backend가 아니다. 결과는 본 checklist의 별도 후보 결과로만 기록한다.

## 상태 정의

| 상태          | 의미                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| **통과**      | 기대 결과를 자동 회귀 또는 실제 runtime에서 관찰했고 근거가 아래에 남아 있음  |
| **부분 통과** | 특정 구현/runtime 또는 핵심 경로에서 확인했지만 전체 연결 경계/장애 조건이 확인되지 않음 |
| **미검증**    | 현재 acceptance evidence가 없거나 재현 실행을 하지 않음                       |
| **실패**      | 실행 결과가 기대 결과와 다르거나 검사 명령이 실패함                           |
| **차단**      | 현재 환경에서 필요한 실제 client, 계정, fixture 또는 안전한 test 환경이 없음  |

“코드가 있음”은 통과 근거가 아니다. 운영 자료를 대상으로 위험한 삭제·대량 이동을 재현하지 않는다. destructiveness가 있는 scenario는 격리 workspace, 별도 temporary root 또는 transaction rollback fixture를 사용한다.

## 릴리스 판단

현재 증거는 cloud file sync의 핵심 성공 경로와 몇 가지 복구 경로가 실제 데이터에서 작동했음을 보인다. 현재 stable runtime에는 10개 pending local item이 있으며 Cloudflare 429로 전송을 확인할 수 없다. 따라서 **모든 동기화 로직 검증 완료 또는 무조건 정상** 판정은 내리지 않는다. Worker 회복 후 이 pending 항목들이 원격에 수렴하는지와 다음에는 offline/restart, three-client collaboration, auth/rate limit failure injection, Production API root-switch E2E, move/delete의 충돌 순서, scale 성능을 격리 환경에서 검증한다.

세부 contract는 [folder sync](../workspace/pkms/folder-sync/README.md), [reconciliation](../workspace/pkms/folder-sync/reconciliation.md), [durability and recovery](../workspace/pkms/folder-sync/durability-recovery.md), [server protocol](../workspace/pkms/folder-sync/server-protocol.md), [UI acceptance](../workspace/pkms/folder-sync/ui-acceptance.md), [구현·배포 상태](../workspace/pkms/folder-sync/implementation-status.md)를 따른다.
