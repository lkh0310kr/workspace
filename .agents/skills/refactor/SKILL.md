# 저장소 전체 리팩터링 진행 지침

작업 단위는 파일 하나가 아니라 **저장소 전체의 조사 범위와 단계별 작업 큐**다. 모든 적격 코드 영역을 평가하되, 개선 근거가 없는 코드는 억지로 바꾸지 않는다.

## 0. 언어와 기본 원칙

- 사용자와의 진행 상황, 조사 계획, 작업 큐, 체크포인트, 결과 보고는 **한국어로 작성한다**. 코드 식별자·명령어·경로·공식 제품명은 원문을 유지하고 필요하면 한국어로 설명한다.
- 저장소에 생성하거나 갱신하는 계획·진행 문서도 한국어로 작성한다. 상태값은 정해진 영문 열거값을 사용해도 되지만, 그 뜻을 한국어로 설명한다.
- 공개 API, IPC, 저장 형식, 외부 호출 횟수와 순서, 오류·재시도·취소 동작, 빌드 결과를 보존한다. 사용자가 별도로 허용한 변경만 예외다.
- 시작할 때 Git 상태, 적용되는 `AGENTS.md`, 저장소 구조와 검증 명령을 확인한다. 기존 사용자 작업을 보존하고 `git reset --hard` 같은 파괴적 정리를 하지 않는다.
- 운영 데이터, 배포, 의존성 업그레이드, 마이그레이션은 기본 범위에 포함하지 않는다.
- 확인한 파일·경로와 미확인 영역을 구분한다. 테스트를 약화하거나 스냅샷만 새 결과에 맞춰 회귀를 숨기지 않는다.
- 변경은 책임 혼재, 복잡한 분기, 중복 규칙, 경계 위반, 테스트 곤란 등 실제 문제를 근거로 정당화한다.

## 1. 전수 조사 범위 고정

1. Git 루트, 브랜치, `git status --short`, 언어·패키지·앱 구조, 지침과 테스트 명령을 확인한다.
2. `git ls-files`를 기준으로 추적 파일을 조사한다. 생성물·벤더·빌드 산출물·잠금 파일·대용량 정적 자산은 경로와 제외 근거를 기록한다. 테스트와 설정 파일은 관련 영역에 배정한다.
3. 실제 저장소 구조에 따라 서로 겹치지 않는 조사 영역을 나눈다. 디렉터리 이름을 미리 가정하지 않는다.
4. 각 영역에 고유 ID, 경로, 파일 수, 진입점, 외부 계약, 주요 테스트, 조사 담당, 상태를 기록한다.
5. 모든 적격 추적 파일을 정확히 하나의 조사 영역에 배정한다. 공통 설정·공유 파일의 수정 소유자는 별도로 지정한다.
6. 가능한 범위에서 기본 테스트·타입 검사·빌드 기준선을 확인한다. 기존 실패와 환경 문제를 구분해 적는다.

**범위 통과 조건:** 전체 영역 인벤토리와 제외 근거를 기록하기 전에는 전체 계획이 완료됐다고 말하지 않는다. 한 앱이나 파일의 계획은 전체 계획이 아니라 하위 작업이다.

## 2. 병렬 탐색

- 실행 환경이 subagent를 지원하면 서로 독립적인 영역에 읽기 전용 조사 담당 2~4명을 배정한다. 상위 담당자는 범위와 통합을 책임진다.
- 각 조사 담당에게 담당 경로, 읽기 전용 원칙, 분석 목표, 다른 담당자의 경로, 제출 형식을 명시한다. 조사 담당은 파일을 수정하지 않는다.
- 결과는 다음 항목을 근거와 함께 간결하게 제출한다: `paths_reviewed`, `entrypoints`, `public_contracts`, `test_commands`, `refactor_candidates`, `risk`, `dependencies`, `no_change_reasons`, `unreviewed_paths`.
- 병렬 조사 결과의 누락 영역은 다시 배정한다. 환경에서 subagent가 불가능하면 그 사실을 기록하고 순차 조사한다. 병렬 실행을 가장하거나 주장하지 않는다.

## 3. 전체 계획과 작업 큐

- 조사 결과를 `.codex/refactor/MASTER_PLAN.md`와 `.codex/refactor/TASKS.md`에 한국어로 기록한다. 이미 동등한 문서가 있으면 재사용하고 [계획 템플릿](references/plan-template.md)을 따른다.
- 모든 조사 영역을 계획에 포함한다. 후보가 없는 영역도 `reviewed/no-change`로 기록한다.
- 작업은 독립적인 계약·모듈 단위로 나누고 위험도, 예상 가치, 수정 파일 소유권, 검증 명령, 선행 작업, 배치, 상태를 기록한다.
- 공유 계약 또는 패키지 간 의존성 변경을 먼저 설계하고 선행 작업으로 둔다. 가치가 높고 회귀 위험과 의존성이 낮은 일부터 시작하되 고위험 영역도 별도 검증을 계획해 포함한다.
- 탐색 커버리지(검토된 영역/전체 영역)와 리팩터링 진행률(검증 완료 작업/선정 작업)을 별도로 표시한다. 수정 파일 수를 완료율로 부르지 않는다.

## 4. 한 배치씩 실행

1. 선행 작업이 끝났고 수정 소유권이 겹치지 않는 작업을 고른다. 가능한 경우 2~3개 worker에 병렬 배정한다.
2. 각 작업에 고유 ID, 수정 허용 경로, 보존할 계약, 수정 금지 경로, 검증 명령, 제출물을 지정한다.
3. 관련 검증의 기존 기준선을 확인하고, 작은 논리적 변경을 적용한 다음 같은 검증을 다시 실행한다.
4. 같은 파일, export barrel, lockfile, 공유 테스트 또는 생성 설정을 여러 작업자가 동시에 수정하지 않는다. 공유 변경은 순차 통합하거나 격리된 작업 트리에서 수행한다.
5. 완료 보고에 수정 파일, 계약 보존 근거, 실제 검증 결과, 남은 위험을 적는다.
6. 통합 담당자가 diff를 검토하고 상태를 `validated`, `blocked`, `needs-rework` 중 하나로 갱신한다.
7. 각 배치에서 영역 검증을 수행하고 공유 경계 변경이 누적되면 관련 통합 검증을 한다. 저장소 전체 검증은 통합 지점과 최종 단계에서 수행한다.

## 5. 중단·재개·완료

- 한 번에 끝내기 어려운 작업이다. 일정·토큰·권한·환경 제한으로 중단할 때는 진행 문서에 완료·미완료·실패·다음 작업을 남겨 재개할 수 있게 한다.
- 선정한 작업의 완료와 전체 코드베이스 평가의 완료를 구분한다. 일부 영역만 조사했다면 미조사 영역을 계속 조사한다.
- 마무리 단계에서 독립 검토, 변경 범위 검토, 저장소 필수 테스트·타입 검사·린트·빌드를 수행한다.
- 완료라고 보고하려면 모든 적격 영역이 `reviewed` 또는 사유가 있는 `blocked`이고, 선정 작업이 `validated` 또는 사유가 있는 `deferred`여야 하며, 남은 검증 위험을 기록해야 한다.
- 실패나 제한이 남아 있으면 완료라고 표현하지 않는다. 검증 전에는 배포·push·merge하지 않는다. 커밋은 사용자 요청과 프로젝트 지침에 따른다.

## 6. 한국어 사용자 보고 형식

매 배치 요약에는 다음 항목을 한국어로 포함한다.

- **전체 탐색:** 검토 영역 수 / 전체 영역 수, 제외 영역과 근거
- **작업 현황:** validated / queued / in-progress / blocked / no-change 수와 각 분모의 정의
- **이번 배치:** 작업 ID, 수정 파일·모듈, 구조 개선 내용
- **검증:** 실제 실행한 명령과 결과, 기존 실패, 환경 제한
- **다음 배치:** 우선 작업, 선행 조건, 미해결 위험

전체 요청을 단일 파일 변경으로 축소하지 않는다. 첫 배치가 특정 파일을 다루더라도 전체 영역 목록과 후속 작업 큐를 먼저 만든다.
